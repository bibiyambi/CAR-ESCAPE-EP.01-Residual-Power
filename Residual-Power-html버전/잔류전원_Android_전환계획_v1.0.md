# 잔류 전원 Android 전환 계획

현대자동차그룹 차량용 앱 개발 공모전 출품과 Pleos Connect 에뮬레이터 시연을 위한 실행 계획

작성 기준일 2026년 11월 15일 · 분석 기준 설계서 v2.0과 소스팩 v2.1 · 계획 버전 1.0

## 1 권고안과 우선순위

**Kotlin Android 호스트에 기존 HTML 게임을 WebView로 탑재하고, Pleos Vehicle SDK와 AAOS 주행 제한을 네이티브에서 연결한다.** 이미 구현된 3막과 15개 퍼즐, 그래픽과 음향을 재사용하면서 차량 입력과 앱 실행 환경을 Android로 전환하는 방식이다. 전체 게임을 Compose나 Unity로 다시 작성하면 PT 전까지 검증해야 할 범위가 크게 늘어난다.

출품 분야는 **정차 중 인카 엔터테인먼트**로 잡는다. 핵심 경험은 주차된 차 안에서 차량의 와이퍼 선택 상태와 공조 풍량을 읽어 미스터리의 단서 계층을 바꾸는 것이다. 기본값인 ‘화면 조작 보조 ON’에서는 실차 조작 없이 같은 이야기를 경험한다. OFF에서는 지원 확인을 마친 차량 신호만 사용한다. ON과 OFF는 입력 방식이며, 정차 중에만 실행한다는 조건은 공통이다.

우선순위는 다음과 같다.

1. **11월 15일 접수:** 필수 접수양식과 동의서, 현재 웹 프로토타입의 증거, 이 전환 계획을 준비한다. Android APK 완성 여부와 접수 가능 여부를 구분한다.
2. **PT 이전:** Pleos Connect 에뮬레이터에서 3막 완주, SDK 읽기 입력, 주행 제한, 중단과 저장 복구, 실행 가능한 release APK를 완성한다.
3. **PT 이후:** 오류 수정과 전시 안정화에 집중한다. 실제 차량 검증과 Pleos App Market 입점은 별도 검증 단계로 관리한다.

공식 공지는 **2차 PT에 실제 차량이 필요하지 않고, Pleos Connect 에뮬레이터에서 구동되는 앱을 시연한다**고 명시한다. 따라서 실차 확보를 PT 개발의 선행 조건으로 두지 않는다. 에뮬레이터의 SDK 콜백 검증 결과를 ‘실차 검증 완료’라고 표현해서도 안 된다. 공모전 심사와 App Market 입점 심사도 별개다. [O1][O2]

심사에서는 차량특화성, 창의성, 기술 활용성, 사업성을 필수 평가한다. 세부 배점은 공개하지 않는다. 1차 개발 산출물 가산점은 단계별로 안내되지만, **HTML만 있는 현재 저장소가 소스와 APK 제출 조건을 충족한다고 볼 수는 없다.** 웹 화면 녹화는 프로토타입 시연 자료로 활용할 수 있다. [O4]

### 3.2 확인한 구현과 남은 작업

설계서의 납품 계획은 1막 선행 후 2막과 3막을 후속 제작하도록 되어 있지만, 소스팩은 이미 v2.1로 세 막을 연결했다. Android 전환을 1막부터 신규 제작하는 일로 산정하지 않는다.

2026년 11월 15일 원본을 임시 폴더에 복사해 [기존 규칙 검사](잔류전원_3막_소스팩/validation/v2-rules.test.cjs) **17개**와 [v2.1 회귀 검사](잔류전원_3막_소스팩/validation/v21-regressions.test.cjs) **11개**를 재실행했고 모두 통과했다. 원본 소스와 원본 검증 보고서는 수정하지 않았다.

기존 [v2 브라우저 보고서](잔류전원_3막_소스팩/validation/v2-browser-report.json)에는 정답을 아는 상태의 15개 퍼즐 UI 검증이, [v2.1 브라우저 보고서](잔류전원_3막_소스팩/validation/v21-browser-report.json)에는 수정 범위와 화면 프로필 검증이 기록되어 있다. 이 기록은 기존 자료의 증거이며 이번 분석에서 브라우저 전편 플레이를 재실행한 결과는 아니다. Android 빌드·에뮬레이터 시연·실차 검증도 아직 수행하지 않았다. 45~60분은 설계 목표이며 실측 플레이 시간이 아니다.

### 3.3 전환 전에 해결할 차이와 결함

**첫째, 1막의 필수 차량 입력이 현재 강제되지 않는다.** 설계서 AC06은 각 막에 차량 입력과 추리를 결합한 필수 퍼즐이 있어야 한다고 정한다. 그러나 [1막 탈출 분기](잔류전원_3막_소스팩/engine-v2.js#L134)는 게임 선루프가 열렸는지만 확인한다. 실제 규칙 실행에서도 P01과 P05를 모두 미완료로 둔 채 1막 탈출이 성립했다. 기존 17개 규칙 검사의 전편 진행 경로도 같은 우회를 사용한다.

권고 수정은 P01과 P04의 선택 단서 성격을 유지하고, **P05의 풍량 입력으로 얻는 진행 상태를 P07 최종 탈출의 필수 조건으로 연결**하는 것이다. 단서를 먼저 읽지 않았어도 도구 조사·접기·회전 정답은 계속 받아들인다. 그 후 최종 탈출만 P05 입력 완료 상태와 결합한다. `messageRead`처럼 단서 열람을 강제하는 조건보다, P05가 생성한 별도의 영속 진행 상태를 사용한다. 그래야 ‘발견과 조작의 분리’ 요구도 보존된다. P05가 왜 탈출에 필요한지 장면 피드백을 추가하고 AC06·AC09를 함께 회귀 검증한다.

**둘째, 개발용 정차가 기본으로 켜진다.** [통합 UI 초기화](잔류전원_3막_소스팩/source/v2-app-extension.js#L2)는 `DEVELOPMENT`로 시작하고, 100ms heartbeat가 모의 V00를 만든다. 네이티브가 나중에 차량 빌드를 활성화하는 것만으로는 첫 화면의 일시적 허용을 배제하기 어렵다. 제출용은 HTML 초기 상태부터 `BLOCKED`로 시작하고, 개발용 heartbeat는 개발 flavor에만 포함한다.

**셋째, 일시정지만으로는 주행 중 UI 숨김을 보장하지 못한다.** [현재 안전 처리](잔류전원_3막_소스팩/source/v2-app-extension.js#L70)는 입력 차단과 일시정지 오버레이를 제공한다. Android에서는 주행 제한 또는 상태 불명 시 네이티브가 WebView 전체를 가리고 터치·음향을 차단해야 한다. 게임·동영상·브라우저 UI의 주행 중 제한은 App Market의 공식 지침에도 명시돼 있다. [O8]

**넷째, 복구와 새 게임에서 호스트 상태를 다시 결합해야 한다.** [게임 복원](잔류전원_3막_소스팩/engine-v2.js#L159)은 새 `InputSession`을 만들며 프로필과 V00를 복원하지 않는다. 이는 올바른 기본 원칙이지만, [웹 복원 API](잔류전원_3막_소스팩/app.js)나 새 게임 후 네이티브 프로필 재주입과 새로운 안전 수신이 빠지면 VEHICLE 빌드에서 재개할 수 없다. 모든 엔진 교체를 `engineReady` 재협상으로 연결한다.

**다섯째, 와이퍼의 모터 상태와 선택 모드는 다르다.** 공개 Wiper 목록에는 `getCurrentWiperSwitch`와 `getCurrentWiperState`, `registerWiperState`가 구분돼 있다. 상태 콜백을 곧바로 운전자가 선택한 모드로 취급하면 P14가 모터 왕복에 반응할 수 있다. SDK 초기 실험에서 의미를 확인하고, 선택 모드 구독이 없으면 공개 getter의 제한된 주기 조회를 검토한다. 임의 API나 와이퍼 왕복 횟수로 대체하지 않는다. [O10]

## 4 기술 방식과 프로젝트 구성

### 4.1 기술 선택

| 선택지 | 재사용 범위 | 추가 작업과 위험 | 판단 |
|---|---|---|---|
| Kotlin 호스트와 WebView | JS 규칙·DOM/SVG·그래픽·음향 대부분 | 브리지·수명주기·WebView 최적화 | **PT용 권고안** |
| Kotlin과 Compose 전체 재작성 | 이미지와 게임 설계 | 15개 퍼즐 UI·규칙·저장·좌표 재구현 | PT 이후 별도 판단 |
| Unity 등 게임 엔진 전환 | 이미지·스토리·설계 | 장면·입력·차량 SDK 플러그인·빌드 체계 신규 | 현재 일정에서는 제외 |

WebView 탑재가 공모전 또는 입점 승인 자체를 보장하지는 않는다. 2차 PT의 실제 실행 환경, 화면 적합성과 공개 API 사용 범위를 만족하는 Android 앱으로 검증한다.

### 4.2 개발 기준

- 언어는 Kotlin, 빌드는 Gradle Kotlin DSL, JDK 17을 출발점으로 한다.
- 공모전 안내에 맞춰 `minSdk 28` 이상을 사용한다. `compileSdk/targetSdk 35`는 공식 샘플을 참고한 초기 제안이며, 채택한 에뮬레이터와 AndroidX 의존성의 최소 요구를 확인해 확정한다.
- Vehicle SDK는 공식 가져오기 문서의 `ai.pleos.playground:Vehicle:2.3.2`를 초기 후보로 한다. Maven 저장소는 `https://nexus-playground.pleos.ai/repository/maven-releases/`다. [O5][O6]
- 조회한 공식 샘플은 README에 2.3.2를 안내하지만 버전 카탈로그는 2.3.1을 가리켰다. 저장소 전체를 무검증 복사하지 않고 실제 의존성 해석 결과·SDK 버전·Vehicle Service 버전을 고정한다. 필요한 typed 호출만 구현한다. [O9]
- SDK 연결 성공, capability, 실제 getter 결과, 구독 또는 조회 동작을 별도 상태로 관리한다. `initialize()` 호출 사실만으로 연결 성공을 표시하지 않는다.
- Android Auto 휴대폰 투사 앱과 구분해 Pleos Connect의 AAOS 앱으로 구성한다. 일반 Android 휴대폰은 웹 UI 개발용으로만 사용하고 SDK 검증 장치로 간주하지 않는다.

### 4.3 저장소 배치 제안

연결된 [개발 저장소](../)에 아래 구조를 새로 만든다. 아래 이름은 앞으로 생성할 경로 제안이다.

```text
프로젝트 루트
├── app/                       Kotlin Android 호스트와 Manifest
│   └── src/main/assets/game/  빌드로 복사한 웹 배포물
├── web/                       원본 HTML 템플릿·JS·CSS·게임 자산
├── tools/                     웹 패키징과 검증 스크립트
├── docs/                      전환 계획·검증 절차·SDK 검증 기록
├── apk/                       제출용 release APK
├── gradle/                    Wrapper와 고정 버전 카탈로그
└── README.md                  심사자가 따라 할 실행 절차
```

현재 자료 폴더는 분석 원본으로 보존하고 저장소에 재현 가능한 소스를 옮긴다. 웹 원본은 `web/` 하나를 기준으로 관리하고 Android assets는 생성물로 만든다. 생성된 HTML과 JS만 고치면 재빌드에서 사라지는 문제를 막는다. 특히 [현재 UI 생성기](잔류전원_3막_소스팩/tools/upgrade_ui.py)는 [1막 렌더러 원본](잔류전원_3막_소스팩/source/act1-app.js)과 [통합 확장 원본](잔류전원_3막_소스팩/source/v2-app-extension.js)을 합쳐 실행본을 만든다.

한 모듈 안에 다음 책임을 분리하면 PT 범위에 충분하다. 이 시점에 다수의 Gradle 모듈을 만들 필요는 없다.

| 구성 요소 | 책임 |
|---|---|
| GameActivity | WebView, 네이티브 차단 화면, Back 처리, 창 크기와 수명주기 |
| VehicleSession | Vehicle SDK 초기화·연결·해제와 오류 |
| VehicleReadAdapter | capability, 와이퍼 선택값·풍량 읽기, 콜백 또는 제한된 조회 |
| SafetyGate | CarUxRestrictions와 정차 근거, 최신성, 차단 우선순위 |
| GameBridge | 버전·세대 확인, 제한된 메시지 전달, 호스트와 JS 준비 협상 |
| CapabilityProfile | 에뮬레이터·SDK·Service·영역별 검증 결과와 원시값 매핑 |
| SaveRepository | 검증된 게임 snapshot의 원자적 저장과 이전 정상본 |

게임 규칙은 계속 JS 한 곳에서 판단한다. Kotlin이 퍼즐 정답이나 완료 조건을 다시 구현하지 않는다.

## 5 WebView와 웹 배포물 전환

### 5.1 로컬 리소스 로딩

[현재 빌더](잔류전원_3막_소스팩/tools/build.py)는 CSS·JS·JSON·폰트와 WAV를 HTML에 인라인화하고, 실행용 이미지와 SVG는 상대 경로로 남긴다. [index.html](잔류전원_3막_소스팩/index.html)은 약 3.34MB다. 전체 에셋은 약 109.3MB이며 배경 PNG 21개가 약 57.6MB, 게임용 SVG cutout 11개가 약 25.0MB를 차지한다. 이는 원본 파일 합계이고 APK 또는 메모리 사용량이 아니다.

Android에는 AndroidX `WebViewAssetLoader`로 `https://appassets.androidplatform.net/assets/game/` 아래의 패키지 자산을 제공한다. `file://`의 광범위한 접근이나 원격 웹사이트 로딩에 의존하지 않는다. 최초 스파이크에서는 기존 실행용 HTML과 참조 에셋으로 완주 여부를 확인하고, 이후 Android 전용 빌더로 JS·CSS·JSON·WAV를 외부 로컬 파일로 분리한다.

폰트 placeholder, SVG 내부 이미지, 문서·마스크 의존성까지 추적해 실제 필요한 파일만 포함한다. 원본 PNG와 SVG에 내장된 같은 이미지의 중복을 조사한 후 줄인다. 조사 영역과 알파 마스크 정합성을 확인하기 전에는 투명 에셋 포맷이나 크기를 일괄 변환하지 않는다. 배경은 화질 비교 후 WebP 등을 검토하고 현재 장면과 인접 장면만 준비해 메모리 피크를 줄인다.

APK 크기는 release 실측으로 관리한다. GitHub의 파일 업로드 한도에 걸리면 공모전이 허용한 GitHub Releases를 사용한다. 최적화 목표를 맞추기 위해 제출 일정을 늦추지는 않는다.

### 5.2 WebView 설정과 탐색

JavaScript와 DOM Storage는 게임에 필요한 범위에서 활성화한다. 파일·콘텐츠의 포괄적 접근, 혼합 콘텐츠, 임의 새 창·다운로드는 허용하지 않는다. 게임 출처 이외의 탐색과 iframe을 차단하고 release에서 WebView 디버깅을 끈다. 로컬 자산 제공과 브리지에 필요한 최소 설정을 사용한다.

브리지는 origin 제한이 가능한 AndroidX WebKit 메시지 방식의 지원 여부를 확인해 우선 적용한다. 지원하지 않는 WebView라면 자체 로컬 출처 전용의 작은 인터페이스를 사용하되 노출 메서드를 제한한다. 범용 JS 실행·차량 쓰기·파일 읽기 기능을 노출하지 않는다. 현재 인라인 스크립트와 SVG가 있으므로 CSP는 외부 파일 분리와 실제 로딩 검증에 맞춰 도입한다.

Back은 게임 모달 닫기 → 일시정지 → 종료 확인 순서로 처리한다. WebView의 인터넷 방문 기록 뒤로 가기를 게임 화면 이동 대신 사용하지 않는다.

## 6 네이티브와 게임 사이의 계약

### 6.1 준비와 재연결

현재 [읽기 전용 호스트 API](잔류전원_3막_소스팩/source/v2-app-extension.js#L71)는 `configure`, `activateVehicleBuild`, `receiveSafety`, `receiveRaw`, `getContext`를 제공한다. [setHostState](잔류전원_3막_소스팩/source/v2-app-extension.js#L68)는 가시성·가림·여백을 전달한다. 이를 보존하되 시작과 엔진 교체의 준비 절차를 추가한다.

1. Android는 네이티브 차단 화면을 먼저 표시한다. 제출 flavor의 웹 엔진도 `BLOCKED`에서 시작한다.
2. JS가 `gameReady`를 보내며 bridgeVersion, 게임 버전, 저장 schemaVersion을 알린다.
3. 네이티브는 실행 환경과 capability profile을 설정하고 검증된 저장 snapshot을 전달한다. 복원으로 엔진이 바뀌면 준비 협상을 다시 수행한다.
4. Vehicle SDK와 AAOS 제한을 새로 확인한다. 과거의 parked, connected 또는 permission 값을 세이브에서 신뢰하지 않는다.
5. 유효한 V00와 화면 상태를 전달한다. 사용자가 시작 또는 재개를 선택한 다음 게임을 활성화한다.
6. 장면·단말·모드·일시정지가 바뀔 때 JS가 새 입력 컨텍스트를 통지한다. 재로딩마다 별도 `hostGeneration`도 증가시킨다.

`getContext()`만 매 콜백 직전에 읽어서 오래된 차량 값을 현재 퍼즐 이벤트로 다시 포장해서는 안 된다. 콜백을 받았을 때의 원시값·수신 시각·연결 세대·활성 세션을 보존하고, 지연 전달 중 컨텍스트가 바뀌면 폐기한다. 새 단말 활성화 후의 첫 조회를 기준값으로 쓸 경우도 그 조회 요청과 응답의 현재 세대를 검증한다.

### 6.2 최소 메시지 범위

| 방향 | 메시지 | 목적과 검증 |
|---|---|---|
| JS → Android | gameReady, engineReady | 버전과 엔진 교체 확인 |
| JS → Android | inputContextChanged | puzzleId·epoch·step·profile과 활성화 시점 동기화 |
| JS → Android | saveRequested | schema와 허용 필드를 검증한 snapshot 저장 |
| JS → Android | requestAudioFocus | 사용자 재생 요청과 오디오 포커스 협상 |
| Android → JS | configureHost | 실행 환경, 사용 가능한 입력, 빌드 종류 |
| Android → JS | receiveSafety, setHostState | 최신 실행 허용과 가림·크기·가시성 전달 |
| Android → JS | receiveRaw | 현재 세션에 해당하는 읽기 전용 차량 값 |
| Android → JS | saveAcknowledged | 정상 저장 확인 또는 재시도 안내 |

메시지는 허용된 타입·크기·필드만 JSON으로 검증한다. JS 문자열 연결로 SDK 값이나 외부 문자열을 실행 코드에 삽입하지 않는다. 네이티브 큐는 직렬 처리하고 UI 조작은 메인 스레드에서 수행한다. 앱 소스가 제공하는 profile 객체의 `verified:true` 자체를 검증 증거로 취급하지 않는다.

### 6.3 시각과 안정 수신

기존 JS 판정은 epoch 밀리초의 `Date.now()`를 사용하며 안정 수신 700ms, 신선도 2000ms를 적용한다. 둘 다 설계 제안값이다. 네이티브에서는 monotonic clock으로 경과시간·연결 감시를 수행하고, JS 경계에서만 기준을 맞춘 epoch timestamp를 전달한다. 기기 시각 변경·절전 복귀를 감지하면 입력 세대를 갱신하고 미완료 입력을 초기화한다.

변경 알림만 있는 API는 값이 같으면 콜백이 오지 않을 수 있다. 따라서 ‘마지막 변경이 2초 전’과 ‘2초 동안 연결을 확인하지 못함’을 구분한다. V00는 신뢰할 수 있는 현재 상태 재조회 또는 공식 플랫폼 상태 감시로 최신성을 확인한다. 단순 heartbeat로 캐시의 시각만 새로 찍어 안전 신호를 만들지 않는다. SDK 초기 실험에서 조회 비용과 갱신 방식을 확인하고 2000ms 기준을 유지할 수 있는지 결정한다.

## 7 Vehicle SDK 연결과 모드별 동작

### 7.1 공개 API 사용 범위

| 내부 신호 | 공개 문서에서 확인한 연결점 | 검증 후 확정할 항목 |
|---|---|---|
| V00 실행 허용 | AAOS CarUxRestrictionsManager, 플랫폼 주행 제한 가이드 | 게임 실행 허용과 실제 정차 의미의 관계, 추가 정차 근거와 권한 |
| V01 와이퍼 | Wiper의 capability·getCurrentWiperSwitch·getCurrentWiperState·registerWiperState | 선택 모드와 운동 상태 구별, OFF/허용 작동 enum, 구독 또는 주기 조회 |
| V02 풍량 | HVAC의 checkHvacFanSpeedCapabilities·getHvacFanSpeed·registerHvacFanSpeed | 영역, 원시값 타입, LOW/MID의 서로 다른 지원 단계 |
| V03 좌우 음향 | 기존 로컬 게임 녹음 | 차량 기본 밸런스와 분리, 자막 경로 유지 |

메서드 이름은 공개 문서의 연결 후보다. 구체적인 인자·콜백·권한은 고정한 SDK의 실제 타입과 API 문서를 대조한 후 코드를 작성한다. 속도·기어 API 이름을 추정해 구현하지 않는다. 현재 Brake의 공개 목록만으로 주차브레이크 판정이 가능하다고 확정할 수 없고, 크루즈 목표 속도는 현재 차량 속도가 아니다. [O5][O10][O11][O12]

와이퍼 선택 모드의 변화 알림이 없으면 **단말 활성 중에만** 공개 getter를 예컨대 200~500ms 주기로 조회하는 방안을 시험한다. 실제 값·SDK 비용·700ms 안정 판정과의 관계를 측정해 주기를 확정한다. 조회 성공을 물리 조작 발생으로 단정하지 않고 같은 값 반복은 입력 단계를 진행시키지 않는다.

### 7.2 정규화와 지원 프로필

에뮬레이터 이름·버전, Vehicle SDK/Service 버전, 영역 ID, capability 응답, raw 값, 수신 방식, 오류, 검사 일시를 프로필과 증거 로그에 남긴다. 에뮬레이터 프로필과 실제 차종 프로필은 별도로 식별한다.

- V01은 검증한 OFF와 수동 저속 또는 간헐 선택값을 각각 OFF/ACTIVE로 매핑한다. AUTO는 허용 작동에 포함하지 않는다. 비의 유무나 모터 왕복을 추론하지 않는다.
- V02는 capability의 지원 범위에서 구분되는 두 단계를 정해 LOW/MID로 매핑한다. 값 1과 2 또는 퍼센트를 공통값으로 가정하지 않는다. 다중 구역이면 검증한 동일 구역만 읽는다.
- 지원 범위가 겹치거나 null·품질 불명·연결 오류면 UNKNOWN으로 처리하고 진행 중인 700ms 후보를 취소한다.
- SDK 연결과 V00 사용 가능 여부는 와이퍼·풍량 지원 여부와 구분한다. V01/V02 미지원이어도 정차가 확인되면 ON은 플레이할 수 있다. OFF만 비활성화한다.
- OFF 전환은 검증 프로필·연결·읽기 권한·V00·V01/V02 매핑을 모두 확인한 후 허용한다. 모드 전환으로 이미 획득한 아이템과 단서는 유지한다.
- OFF에서 단절되면 일시정지하고 사용자에게 ON 전환을 제공한다. 자동 모드 전환이나 자동 퍼즐 성공은 만들지 않는다. ON으로 바꿔도 V00가 불명이면 계속 차단한다.

권한은 [공식 권한 안내](https://document.pleos.ai/en/docs/pleos-only/connect-sdk-pleos/Vehicle/vehicle-permission)와 실제 API의 `@RequiresPermission`을 대조한다. 문서의 대표 읽기 권한은 Wiper의 `CAR_WINDOWS`, HVAC의 `CAR_CLIMATE`이며, 필요한 V00 경로의 권한을 추가한다. 공식 샘플은 여러 도메인의 control 권한도 포함하므로 Manifest를 그대로 복사하지 않는다. 차량 쓰기 권한과 set 계열 호출은 앱 범위에서 제외한다. 현재 샘플은 차량 권한을 normal로 설명하므로 모든 권한에 위험 권한 런타임 팝업이 뜬다고 가정하지 않는다. capability와 SDK 오류까지 확인해야 사용 가능 판정을 내린다. [O7][O9]

### 7.3 에뮬레이터와 실차의 구분

PT 시연에서는 Pleos 에뮬레이터와 공식 Virtual Console 또는 시스템 UI가 신호의 출처다. SDK를 통해 읽힌 해당 신호를 내부 `sourceMode: VEHICLE`로 전달할 수 있지만 화면·README에는 **에뮬레이터 SDK 입력**이라고 표시한다. 화면 조작 보조 ON의 JS 모의 입력과도 구분한다.

실차 검증 전에는 ‘실차 OFF 지원’이라고 홍보하지 않는다. 이후 검증에서는 차종·영역·SDK·Service 조합별로 V00부터 V02를 다시 확인한다. 현실의 벨트·좌석·미러·선루프·시동은 입력 대상으로 확대하지 않는다.

## 8 실행 허용과 Android 수명주기

### 8.1 V00를 먼저 확정한다

공식 개발 가이드는 AAOS `CarUxRestrictionsManager`에 listener를 등록하고 `onUxRestrictionsChanged()`와 active restrictions를 반영하도록 한다. 게임을 주행 중 사용 가능하게 만드는 Distraction Optimization 선언은 하지 않는다. 플랫폼 차단과 앱 자체 차단을 함께 검증한다. [O12]

다만 **제한 플래그가 없다는 사실이 설계서의 ‘속도 0과 검증된 주차 상태’를 자동으로 증명하지는 않는다.** 첫 이틀의 기술 실험에서 다음 둘을 별도로 확정한다.

1. 플랫폼의 게임 실행 허용 판정을 어떤 공개 상태와 제한 조합으로 받을 것인가.
2. 그 판정이 정차 전용 콘텐츠의 허용 의미까지 보장하는가. 추가 정차 증거가 필요하다면 어떤 문서화된 API와 권한으로 읽을 것인가.

보장된 플랫폼 실행 허용을 V00로 채택하려면 설계서의 속도·기어 조합 제안을 해당 플랫폼 계약으로 명시적으로 개정한다. 해당 의미가 확인되지 않으면 근거 없는 `parked:true`를 만들지 않고 차량용 빌드의 시작을 차단한다. 이 경우 개발 flavor로 웹 완주 증거를 준비할 수는 있지만 플랫폼 안전 연동 완료로 표시하지 않는다.

### 8.2 상태별 처리

| 상황 | 네이티브 처리 | 게임 상태 |
|---|---|---|
| 처음 실행·V00 불명 | 게임 화면을 가리고 입력·음향 차단 | 새 검증과 시작 입력 대기 |
| 정차와 가용성 확인 | 시작 또는 재개 버튼 제공 | 사용자 동작 후 플레이 |
| 주행 제한·정차 불허 | WebView 전체 숨김, 오디오 정지, 저장 요청 | 시퀀스·미완료 유지시간 초기화 |
| 시스템 패널 가림·포커스 상실 | 가림 전달, 보수적으로 일시정지 | 미완료 유지시간 폐기 |
| 일반 게임 메뉴 | 메뉴를 표시하고 일시정지 | 확인한 순서 단계는 유지, 진행 중 후보는 폐기 |
| 앱 백그라운드·화면 꺼짐 | 저장, 재생 중지, 필요 구독·조회 정지 | 복귀 후 최신 상태와 수동 재개 |
| SDK 단절·권한 오류 | 프로필 가용성 무효화, 차단 | 자동 성공이나 자동 재개 없음 |
| WebView renderer 종료 | 네이티브 차단 유지, WebView 재생성 | 정상 snapshot부터 복구·준비 재협상 |

창 포커스 상실이 모든 시스템 오버레이를 완벽하게 설명한다고 가정하지 않는다. Lifecycle·window focus·실제 제공되는 플랫폼 가림 신호를 조합하고, 중복 알림은 같은 차단 상태로 합친다. 특히 풍량을 시스템 GNB에서 바꾸면 게임이 가려질 수 있으므로, 복귀 후 새 단말 입력으로 재개하는 동선을 실제 에뮬레이터에서 시험한다. 가림 중 입력을 과거 이벤트로 누적해 자동 완료하지 않는다.

최종 차단 책임은 네이티브가 가진다. JS timer 지연·오류·미응답 상태에서도 게임 화면과 오디오가 계속 노출되지 않도록 한다. 내부 성능 목표는 제한 콜백 수신 후 250ms 이내 차단 시작으로 제안하고 기기에서 측정한다. 이는 공모전의 공식 수치가 아니다.

## 9 저장과 음향 및 차량 화면 적응

### 9.1 저장

첫 WebView 스파이크에서는 DOM Storage를 켜 기존 [저장 로직](잔류전원_3막_소스팩/app.js)의 정상 동작을 확인한다. PT 버전에서는 JS 게임 snapshot과 네이티브 저장소의 책임을 다음과 같이 정리한다.

- 게임 snapshot의 schemaVersion 2와 v1→v2 변환을 유지한다. 네이티브 저장 envelope는 별도 버전·게임 버전·저장 순번을 가진다.
- 네이티브를 최종 영속 저장의 기준으로 삼고 앱 내부 저장소에 원자적으로 쓴다. 이전 정상본을 한 개 보존한다. checksum은 손상 감지용이며 보안 인증으로 취급하지 않는다.
- 퍼즐 완료·아이템 획득·화면 이동·설정 변경과 Lifecycle 중단 시 저장한다. 중요 진행은 앱 종료 시점에만 의존하지 않는다.
- 기존 localStorage를 한 번 가져올 때 검증 후 네이티브 저장 성공을 확인한다. 실패하면 원본을 보존한다. 네이티브 모드에서는 웹과 네이티브가 서로 다른 최신본을 계속 쓰지 않도록 저장 경로를 통일한다.
- 정차 허용·연결·권한·현재 입력 epoch와 진행 중인 700ms 후보는 복원하지 않는다. OFF 저장으로 복귀해도 새 사전 점검을 거친다.
- 손상·알 수 없는 schema는 자동 덮어쓰지 않는다. 백업 복구 또는 새 게임을 선택할 수 있게 한다.

브라우저와 Android WebView는 저장 출처가 다르므로 기존 Chrome 플레이 기록이 자동 이전되지는 않는다. 필요하면 사용자가 명시적으로 내보내고 가져오는 기능을 후속 범위로 두며 PT 필수 기능으로 늘리지 않는다.

### 9.2 음향

현재 Web Audio와 HTML 오디오를 동시에 제어할 공통 pause·mute·resume 경계를 만든다. Kotlin은 Android Audio Focus를 요청하고, 포커스 손실·시스템 음성·백그라운드·주행 제한에 따라 모든 음원을 중단한다. 복귀해도 사용자 재생·재개 입력 전 자동 재생하지 않는다. 포커스 손실 때 JS가 응답하지 않는 경우 네이티브 WebView 중지·재생 세션 제거로 이어지는 경로도 검증한다.

녹음의 L/R는 게임 파일의 채널이다. 차량 전체 오디오 밸런스를 변경하지 않는다. P10은 자막만으로도 해독 가능해야 하고, P04도 청취 상태와 자막 접근성을 Android에서 검토한다. 재생 시간이 백그라운드에서 흘러 퍼즐이 완료되지 않게 한다. TTS·STT·외부 음성 인식은 이번 이식에 필요하지 않다.

### 9.3 창 크기와 조작

[기존 12개 화면 프로필](잔류전원_3막_소스팩/profiles.json)은 회귀 프리셋으로 유지하되 실제 앱 창 크기를 대신하는 하드코딩 값으로 사용하지 않는다. 공식 레이아웃 가이드에 따르면 시스템 상태바·드라이빙뷰·GNB·공조 패널과 앱 윈도는 구분되며, 시스템 UI가 앱 위를 가릴 수 있다. [O13]

Android의 실제 창 경계와 insets로 WebView 크기를 결정한다. 네이티브 px, dp, WebView CSS px 변환을 측정하고 중복 여백 적용을 막는다. 화면 전체를 가정하거나 GNB를 덮지 않는다. 원본 1672×941 장면과 조사 영역은 같은 contain 변환을 적용하고, 소지품·수첩·모달 UI는 가용 영역에 맞춰 재배치한다.

PT 검증은 대표 가로 창과 가장 좁은 분할 창을 우선하고, 이후 12개 프리셋과 글자 100/130/150% 조합을 검사한다. 작은 물건은 기존 조사 목록으로 접근할 수 있어야 한다. 메뉴·닫기·확인·재개 버튼을 시스템 UI 아래에 숨기지 않는다. 실제 터치 목표 크기와 글자 대비는 해당 Pleos 가이드와 기기 검증으로 확정한다.

### 11.2 초기 중단 기준과 범위 축소

11월 17일까지 V00 경로와 V01/V02의 의미가 확인되지 않으면 차량 입력 개발이 완료될 것이라고 약속하지 않는다. 공개 API로 불가능한 기능은 공식 공지에 따라 후속 계획으로 옮긴다. 이미 검증된 ON과 정차 차단, 3막 완주, 저장·음향을 우선 완성하고 OFF는 사유와 함께 비활성화한다. 이 경우 PT 기술 활용성과 차량특화성 증거가 약해진다는 점을 제출 설명에도 반영한다.

V00까지 확보되지 않은 개발용 모의 빌드는 전시 가능한 차량용 완성본으로 간주하지 않는다. 반대로 V00만 검증되고 V01/V02가 미지원이면 정차용 ON 버전은 유지할 수 있다. 지원하지 않는 OFF를 가짜 차량 신호로 보충하지 않는다.

실차 테스트, 음성 AI, 서버, 계정, 온라인 명단 송신, 실차 제어, 신규 에피소드는 PT 필수 범위에서 제외한다. 전시 준비 기간은 기능 확장의 여유 기간으로 계산하지 않는다. [O1][O4]

### 13.2 PT 데모 순서 제안

발표 배정 시간이 아직 확정되지 않았으므로 약 5분의 기술 데모 구간을 내부 연습용으로 제안한다.

1. 에뮬레이터 버전·화면과 정차 전용 앱임을 설명하고 첫 화면에서 시작한다.
2. 화면 조작 보조 ON으로 단말·단서·수첩·저장을 보여 준다.
3. capability 확인 후 OFF로 전환하고 에뮬레이터 시스템/Virtual Console에서 와이퍼 또는 풍량을 바꾼다. 앱에 차량 쓰기 호출은 없다.
4. 신호 수신 후에도 영상 정렬·회로 접점 선택 같은 별도 추리가 필요함을 보여 준다.
5. 공식 에뮬레이터 조작으로 주행 제한이나 연결 오류를 발생시켜 UI·음향 차단과 수동 재개를 보여 준다.
6. 각 막과 엔딩의 녹화 자료로 전체 완주를 보완한다. 필요하면 별도 시연 flavor의 명시적 체크포인트를 사용하고 저장 데이터를 몰래 주입하지 않는다.

단축 시연용 세이브·체크포인트가 필요하면 정상 경로로 만든 고정 데이터를 사용하고 제출 release에 치트 해제 기능을 넣지 않는다. 3막 전체 기능 검증 영상과 PT용 짧은 영상은 목적을 구분해 준비한다.

### 13.3 제출 묶음

- 공식 접수양식과 참가자 동의서. 이 계획서만으로 필수 양식을 대체하지 않는다.
- 앱 이름·한 줄 소개·실행 방법·필요 설정·에뮬레이터 버전과 화면 규격·APK 위치를 갖춘 저장소 README.
- 서명된 release APK와 APK SHA-256, 해당 소스의 commit hash, Gradle과 SDK 고정 버전.
- ON 완주와 에뮬레이터 OFF, 미지원 OFF 차단, 주행 제한과 복귀를 보여 주는 증거 영상·검증표.
- 폰트 라이선스와 그래픽·음성의 제작 출처·사용 조건. [기존 생성 이력](잔류전원_3막_소스팩/source/v2-art-provenance.json)과 [폰트 라이선스](잔류전원_3막_소스팩/assets/fonts/OFL-NanumGothic.txt)를 출발점으로 확인한다.
- 비밀값 없이 재현 가능한 설정 예시. 로컬에 제공된 SDK 자격 정보·서명키를 저장소·계획서·영상에 복사하지 않는다. 공개 클라이언트 앱에 secret을 넣는 방식이 인증 설계가 되지 않음을 고려해 실제 SDK 요구에 맞춘다.
